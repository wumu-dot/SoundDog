### 1.1 核心目标（一句话）

### 1.4a 帧协议最终决议（2026-09-01 阶段1/2 人确认，防自造）

- **可调参数集（全套 5 项，含编译期默认，禁止自造）**：

  | 参数ID | 名称       | 默认值 | 范围                    | 传输格式                        |

  | 0x01 | 阈值 TH    | 6.0 | 1.0\~20.0             | `uint16_t` 定点 ×100（600=6.0） |
  | 0x02 | 触发连续帧 30 | 30  | 1\~100                | `uint16_t`                  |

### 1.4c 傻瓜式操作单（照做即可）

#### 帧格式定义（人确认，防自造；PC 端与板端必须一致）

```
帧结构（固定长度，共 8 字节）：
  字节0  0xA5          帧头
  字节1  0x01          地址码（本设备=1）
  字节2  0x21          命令码（0x21 = 写单一参数）
  字节3  0xXX          参数 ID（0x01~0x05，见 §1.4a 表）
  字节4  0xXX          参数值低字节（uint16，LSB-first）
  字节5  0xXX          参数值高字节
  字节6  0xXX          CRC16 高字节（大端）——见下方发送序
  字节7  0xXX          CRC16 低字节
```

> 定界约定：**固定 8 字节帧长**即帧尾判定（收到 8 字节一帧即完整），无需独立 0x5A 帧尾字节——
> 因帧头 0xA5 已在字节0，且总长固定，CRC16 覆盖全帧(字节0\~5)含帧头，合法帧靠 CRC 保证完整性。
> 这避免「0x5A 出现在数据域」与 CRC 覆盖边界冲突。A5-02 的「帧尾 0x5A」语义在本最小帧内
> 由**固定帧长 + 全帧 CRC** 实现（R27：简洁设计优先；若后续 A5-02 需独立帧尾，此处在该 FEAT 内对齐）。
> 阶段3 代码以此 8 字节布局为准，文档与实现不得冲突。

##### CRC16 来源（2026-09-01 实采，可点击验证，禁止口头声称）

- 参数权威定义：官方规范 [modbus.org Modbus Application Protocol Spec V1.1b3](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf)（CRC 校验在 RTU 模式，参数 poly 0x8005/init 0xFFFF/反射/xorout 0）。

- 官方 CRC 表实现（验证 `crc16_reverse_table`=0xA001 反射表，标注 "used by modbus"）：[qModMaster/3rdparty/libmodbus/modbus-rtu.c](https://github.com/zhanglongqi/qModMaster/blob/master/3rdparty/libmodbus/modbus-rtu.c)

- 独立实现（标注 `Reverse: 0xA001 (used by modbus)`）：[rikeyone/algorithms/crc16.c](https://github.com/rikeyone/algorithms/blob/master/crc16.c)

- 参数标准对照表（CRC16\_MODBUS 行：poly 0x8005/init 0xFFFF/数据低位在前）：[CSDN CRC16常见的标准](https://blog.csdn.net/zdwcmy/article/details/135491308)

- 官方手算样例 & 字节序：`01 03 00 00 00 01` → CRC 0x0A84 → 完整帧 `01 03 00 00 00 01 84 0A`（Modbus 低字节先发；本项目 A5-02 约定改为**大端**发送，见上）——[docs.chipkin.com Modbus CRC & LRC 排错](https://docs.chipkin.com/articles/modbus-crc-lrc-error-checking-and-troubleshooting/)

- 逐字节帧解析状态机（阶段3 代码结构参考）：[EmreSoftware/STM32-UART-Protocol\_LED-Control](https://github.com/EmreSoftware/STM32-UART-Protocol_LED-Control)（WAIT\_HEADER→LENGTH→DATA→CRC→FOOTER）、[Coskunruhi/STM32-UART-Protocol-Parser-with-CRC16](https://github.com/Coskunruhi/STM32-UART-Protocol-Parser-with-CRC16)（poly 0x8005 + 大端 CRC 发送，与本项目最贴近）、[skb666/stm32f4\_iap](https://github.com/skb666/stm32f4_iap)（PARSE\_STAT 帧头状态机）、[CSDN 串口 DMA+状态机接收 0xA5 0x5A](https://blog.csdn.net/qq_45315034/article/details/147908454)。

CRC16 算法（Modbus 标准，参数来源见上 + crcmod 库交叉锁定）：
多项式 0x8005（反射表序 0xA001） / 初值 0xFFFF / 反射输入输出 / 结果异或 0x0000
**发送序 = 大端（高字节在前，低字节在后）**——三源实测一致：
crcmod(`05 06 05 02 00 01`)=0x82E8 → 帧尾 `82 E8`
crcmod(`01 03 00 00 00 0A`)=0xCDC5 → 帧尾 `CD C5`
校验向量（阶段4 用此实测，crcmod 已验证）：
`A5 01 21 01 20 03`（TH=8.0 帧）→ CRC16 = 0x1327 → 帧尾 `13 27`
`A5 01 21 02 28 00`（触发帧40）  → CRC16 = 0xD290 → 帧尾 `D2 90`
`A5 01 21 04 64 00`（滑窗100,拒改帧） → CRC16 = 0x1344 → 帧尾 `44 13`
⚠️ 踩坑记录（R31 编码前预研）：第一版手写文档把向量写成 0xF4D7 且发送序写成低字节先，均为**自造错误**；
已用 crcmod(0x18005, rev=True, initCrc=0xFFFF) 交叉验算钉死为 0x1327 / 大端。A5 系列须沿用本约定。
