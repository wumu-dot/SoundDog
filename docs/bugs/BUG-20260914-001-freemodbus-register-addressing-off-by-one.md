# FreeModbus 保持寄存器帧地址 off-by-one：合法写错落寄存器 → 假"越界 0x02/链路断"

- **Bug ID**：BUG-20260914-001
- **严重等级**：P1-功能（A4-04 Modbus 参数下发/回读不可用，且被长期误判为 RS485 硬件链路故障，阻塞阶段 4 验证）
- **发现日期**：2026-09-14
- **修复日期**：2026-09-14
- **关联 FEAT**：FEAT-A4-04（参数可调，Modbus 迁移）

## 现象描述

用 USB-RS485 适配器（COM5）经 MAX3485 向板子上 FreeModbus 从站发 FC06 写保持寄存器：

- 发 `01 06 00 01 03 20`（自以为写 TH＝8.0）→ 返回 **异常 `01 86 02`（MB_ENOREG）**，明明 800 在 TH 合法范围 [100,2000] 内；
- 发 `01 06 00 01 00 32`（TH＝0.5，理当越界拒绝）→ 却**回显生效**；
- FC03 读 0x0001 起 5 个 → 返回异常 `01 83 02`（读路径也判"未映射"）。

现象完全与 `param.h`（TH∈[100,2000]、MODBUS_REG_HOLDING_NUM=5）矛盾，且**重编重烧全量固件后依旧复现**，一度怀疑固件回调和真实源码不一致。

连带：前期反复出现"适配器发帧但板子 STATUS 灯不闪/收不到"，被误判为 RS485 链路或适配器硬件故障，拉扯了大量万用表/回环排查。

## 复现步骤

1. 板子跑正常功能固件（`MBSlavePollTask` 内 `eMBInit(MB_RTU,0x01,3,115200,MB_PAR_NONE)` + `eMBEnable` + `eMBPoll`）。
2. 从 PC 经 USB-RS485 适配器经 MAX3485 直连板上 A/B/GND。
3. 用 1 基址习惯发帧：写 TH 用帧地址 `0x0001`、读快照用 `01 03 00 01 00 05`。
4. 观察：写被异常 0x02 拒（值其实合法）、读被异常 0x02 拒。

## 根因分析（一句话）

**FreeModbus 在调用寄存器回调前内部执行 `usRegAddress++`（`mbfuncholding.c:87/123/183/258`），回调收到的 `usAddress = 帧地址字段 + 1`；而 `modbus_app.c` 用 `usAddress-1` 做偏移，两项抵消后实际命中偏移 = 帧地址字段本身。因此协议对外是 0 基址**：

- 帧地址 `0x0000` → 回调偏移 0 → TH；
- 帧地址 `0x0001` → 偏移 1 → ALARM_CNT（写 TH 却落到 ALARM，800 超 ALARM 上限 100 → 假 0x02）；
- FC03 读 `0x0001` 起 5 → 回调地址 2、2+5-1=6 > NUM=5 → 假"未映射"0x02。

**修正后（0 基址）实测逐项吻合**：`0x0000` 写 TH 600/2000 回显、50 越界拒；`0x0001` 写 ALARM 40 回显；`0x0003` 写滑窗 100 回显；FC03 读 `0x0000`×5 返回 `03 20 00 28 00 3C 00 64 00 1E`（800/40/60/100/30），与写入值逐字一致。`modbus_app.c` 本身符合 FreeModbus 约定，**固件无 bug**；错的是手写测试帧/文档采用了 1 基址。

三源佐证（R27）：`mbfuncholding.c` 源码逐行（`usRegAddress++`）；FreeModbus 官方 demo 以帧地址 0 起算 + 应用层 `usRegHoldingStart` 语义一致；跨量问题（对本仓库即为 gen_param_frames.py 预先默认 0x0001 起）无第三方，按源码实判定案。

## 修复方案

1. **测试脚本** `scripts/gen_param_frames.py`：`CASES`/`BAD_CASES`/FC03 读帧全部改为 0 基址（TH=0x0000、ALARM=0x0001、RELEASE=0x0002、滑窗=0x0003、窗内=0x0004）。
2. **文档注释**：`BSP/param.h` 寄存器映射注释、"App/modbus_app.c:reg_off_to_pid` 上方坑注释、`gen_param_frames.py` 头 docstring 统一改为"帧地址 0 基址" + 说明 FreeModbus `usRegAddress++` 抵消机理。
3. **不改固件代码**：`modbus_app.c` 偏移逻辑正确，保持现状；仅在关键处加注释防止被当 bug"修正"回去。

## 验证方式

`python scripts/gen_param_frames.py --com COM5` 在真实链路回读：
- 5 个正常写全部 `-> OK 已生效（回显原帧）`；
- 3 个越界写全部 `-> 异常0x02（MB_ENOREG 越界拒绝）`；
- FC03 读快照返回 `01 03 0A 03 20 00 28 00 3C 00 64 00 1E ...`，`TH=800 触发=40 解除=60 滑窗=100 窗内=30`，与写入值逐字一致。

**验证条件**（必填，R25）：
- 硬件/环境：ST-Link/OpenOCD 烧录功能固件 + USB-RS485 适配器(COM5, CH340) A/B/GND 直连板上 MAX3485；
- 验证的因果链：验证了"合法写→回显、越界写→0x02、读快照→与写入值一一对应"的完整读写闭环（非仅"收到字节"）；且同一固件在 1 基址下发时复现 0x02、0 基址下发时全过，反证根因在帧基址而非链路；
- 结论级别：功能正常（Modbus 参数读写端到端验证通过）。RS485 链路经「板→PC 收 30×MBT」+「板收一字节回一字节 16 回 16×E」+「Modbus 写读全过」三重独立证据确认真通。

## 通用教训（提炼至 lessons\_summary）

1. **FreeModbus 寄存器帧地址是 0 基址**：栈会在回调前 `usAddress++`，应用层 `usAddress-1` 抵消后 = 帧地址本身。手写测试帧/文档一律按 0 基址对齐 TH=0x0000；发 0x0001 会落到下一个寄存器，出现"合法值被异常 0x02 拒"的假象。见 R34。
2. **"合法值却异常 0x02"先怀疑地址基址错位，再怀疑越界逻辑/链路**：此次该假 0x02 把排查引向 RS485 硬件和适配器，浪费大量时间（见 R35）。
3. **链路排查先锁定"PC 往哪个 COM 发"**：本板调试口(USART1)与 RS485 适配器口(COM5)是两个独立 COM，灌错口会表现为"status 灯不闪/收不到"，被误判为硬件坏（见 R35/R36）。
