# CRC16 校验向量自造错误（0xF4D7/低字节先发 → 实为 0x1327/大端）

- **Bug ID**：BUG-20260901-001
- **严重等级**：P2-一般（阶段1/2 规划文档校验向量错，未落盘固件，但一旦照抄会封锁 A4-04 阶段4 与 A5 系列协议验证）
- **发现日期**：2026-09-01
- **修复日期**：2026-09-01
- **关联 FEAT**：FEAT-A4-04（A4-04/A5 系列帧协议统一沿用本约定）

## 现象描述
A4-04 阶段1/2 帧协议设计时，手写校验向量为：
1. CRC16 = `0xF4D7`（自造值，与实际不符）
2. 发送序描述为"低字节先发"（自造序，与项目 A5-02 大端约定不符）

随后用 `crcmod`（权威第三方库，[crcmod / PyPI 官方文档](https://pypi.org/project/crcmod/)，CRC 参数 `poly=0x18005, rev=True, initCrc=0xFFFF`，对应 CRC16-Modbus）交叉验算，正确向量为 `0x1327`，且发送序为大端（高字节在前）。

## 复现步骤
1. 在 FEAT-A4-04 手写参数帧 CRC 校验向量为 `0xF4D7`、发送序为低字节先发。
2. 用 `crcmod` 对 `A5 01 21 01 20 03`（TH=8.0 帧）计算 CRC16。
3. 观察：crcmod 结果为 `0x1327`；按"低字节先发"组帧会得到 `27 13`，与打包器大端输出 `13 27` 相反 → 板端/PC 端解析不一致，验证必失败。

## 根因分析
规划阶段依赖人工手写数值/字节序，未在落盘前用权威实现交叉锁定——违反本项目"数据手册/权威实现为准、禁止自造"的纪律。

## 修复方案
`scripts/gen_param_frames.py` 中统一用 `crc16_modbus` 位算法框架，且与 `crcmod(0x18005, rev=True, initCrc=0xFFFF)` 逐向量交叉验算钉死；CRC 发送序统一为大端。校验向量改为：
- `05 06 05 02 00 01` → `82 E8`
- `01 03 00 00 00 0A` → `CD C5`
- `A5 01 21 01 20 03`（TH=8.0）→ `13 27`

## 影响文件
- `docs/features/FEAT-A4-04-参数可调.md`（§1.4c 校验向量/发送序已更正，行 111-118 内联踩坑登记）
- `scripts/gen_param_frames.py`（CRC 计算逻辑）
- A5 系列协议帧（沿用本约定，按大端发送）

## 验证方式
`crcmod` 与 `gen_param_frames.py` 位算法对所有用例向量（含官方 `01 03 00 00 00 0A → CD C5`）双向一致 PASS；核对发送序为大端。

**验证条件**（必填，R25）：
- 硬件/环境：PC，Python `crcmod` 库（`pip install crcmod`），无硬件依赖
- 验证的因果链：已验证"已知输入字节序列 → 第三方权威库输出固定 CRC"（crcmod 与 bit 算法逐向量比对一致），非"数值非零"级验证
- 结论级别：功能正常（计算层）

## 通用教训（提炼至 lessons_summary）
协议校验字段（CRC/校验和/字节序）涉及自造数值时必须用权威/第三方实现交叉锁定，不可凭"看起来对"手写——`crcmod` 等标准库为一等验证源；并对齐发送字节序（本项目 A5-02 大端），防止板端/PC 端静默错位（R27/R31 编码前预研）。
