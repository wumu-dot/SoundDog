# BUG-002 详解：为什么 I2S 收到的数据 3/4 是"垃圾"——INMP441 数据提取问题全解

> 关联：[BUG-20260816-002](../bugs/BUG-20260816-002-i2s-data-alignment.md)（已关闭 v10）
> 关联 FEAT：FEAT-A1-音频采集链路 / FEAT-A1-01 / FEAT-A1-02
> 写作目的：把这次踩了 12 天的坑（08-16 发现 → 08-28 确诊）从原理层讲透，避免下次在任意 I2S 器件上重蹈覆辙。

---

## 1. 一句话总结

**麦克风输出的每一个声音采样，在 DMA 缓冲区里占了 4 个 32-bit 字的位置，其中只有第 1 个字是真的音频；v9 之前的代码把 4 个字全当音频用，等于 4 个样本里 3 个是假的，max 统计被假样本"淹没"。**

---

## 2. 背景知识：I2S 协议到底在传什么

### 2.1 三根线各干什么

I2S 只有 3 根信号线（本工程：SCK=PB3、WS=PA4、SD=PB5）：

| 线 | 名字 | 类比 |
|----|------|------|
| SCK | 位时钟 | 传送带的速度——每滴一声，SD 线上传 1 个 bit |
| WS  | 字选择（左右声道） | **车厢分隔铃**：WS=0 说"现在是左声道车厢"，WS=1 说"现在是右声道车厢" |
| SD  | 串行数据 | 传送带本身——bit 一个一个往上放 |

关键规则：**WS 每翻转一次，代表一个"声道槽"（slot）开始**。标准 Philips I2S 里，一个槽 = 16 或 32 个 SCK 周期。

### 2.2 本工程的时钟配置（数字要对上）

```
采样率 = 16 kHz（设计值）
每采样 64 个 SCK（32-bit 槽 × 左右 2 个槽，立体声帧格式）
→ SCK = 16000 × 64 = 1.024 MHz
```

STM32 端配的是 `I2S_DATAFORMAT_32B`：**每 32 个 SCK 收一个 32-bit 字，DMA 搬一次**。

### 2.3 INMP441 的怪脾气（问题的种子）

INMP441 是**单声道**麦克风，但它遵循立体声 I2S 帧格式：

- L/R 接 GND → 它只在**左声道槽**发声，右声道槽期间 SD 引脚**松手不驱动**（高阻态）
- 它的"发声"不是 32-bit，而是 **24-bit 数据 + 1 bit 驱动标志**，塞在 64 SCK 的槽里

所以电平上实际发生的事（时间从左到右）：

```
WS:   ________                    ________
      左声道(64 SCK的一半=32SCK)   右声道槽(32 SCK)

SD:   [bit23..bit0 共24bit音频] [驱动位1] [31个SCK不说话]  [整槽高阻]
       ←-------- 左槽 --------→                          ←-- 右槽高阻 --→
```

**注意**：左槽里 INMP441 只用了 24+1=25 个 SCK，剩下 7 个 SCK 它也不驱动。

## 3. 问题核心：STM32 的"取货窗口"和麦克风的"发货节奏"没对齐

这是整个 bug 的心脏，用仓库类比：

- **INMP441 是发货员**：它按自己的节奏往传送带（SD 线）上放货。每个立体声帧（64 SCK）它只发一次货：24-bit 音频放在**左槽的前 25 个 SCK**，其余时间手撒开（高阻）。
- **STM32 是收货员**：它每 32 个 SCK 装一个箱子（32-bit 字），让 DMA 搬进仓库。**它不管箱子里装的是货还是空气**。

现在把两边的节奏画在一条时间轴上（每格 = 32 SCK = 1 个 DMA 字）：

```
时间轴:    |←— word0 —→|←— word1 —→|←— word2 —→|←— word3 —→|
           |           |           |           |
INMP441:   [24bit音频+标志，7SCK高阻][   高阻，不驱动   ][   高阻   ][   高阻   ]
           ←—— 左槽(32SCK) ——→ ←—————— 右槽(32SCK) ——————→
STM32:      收成 word0          收成 word1      收成 word2    收成 word3
```

**每 4 个 DMA 字构成一个周期，128 SCK = 2 个立体声帧 = 2 次采样？不对——是每 64 SCK（2 个字）一个立体声帧**。但实测 dump 显示周期是 4 个字，说明 STM32 的字窗口和 INMP441 的槽窗口**错开了半槽（16 SCK）**——这正是 BUG-002 标题里"相位偏移"的实锤。错位后的实际画面（实测）：

```
word[4k+0] = 0x0000_PPPP   ← 真实音频：24-bit 采样的高 16 位（bits[23:8]）
word[4k+1] = 0x0000_LL7F   ← 同一采样的低 8 位(LL) + 7F 伪迹（SD 松手被上拉到中间电平）
word[4k+2] = 0x0000FFFF    ← INMP441 完全不驱动的槽：上拉电阻把线拉成全 1
word[4k+3] = 0x0000FFFF    ← 同上
```

### 3.1 用实测数据逐字拆解（17:47 日志）

安静时：
```
0000FC0B  →  0xFC0B = -1013   ← 真音频：安静时的底噪+直流偏置，±600 上下
0000B97F  →  0xB9 是同一采样的低 8 位；7F 是 SD 松手后的上拉中间电平
0000FFFF  →  悬空槽，被 4.7kΩ 上拉成全 1
0000FFFF  →  同上
```

吹气时：
```
00008AFF  →  0x8AFF = -29441  ← 真音频：吹气！直接打到 90% 满量程
0000F07F  →  低 8 位变了(0xF0)，说明采样值大到位溢出到低位字节
0000FFFF  →  还是悬空伪迹
0000FFFF  →  同上
```

**看懂这个 dump，就等于亲眼看到了麦克风在说话**——`0000FC0B` 是它安静时的心跳，`00008AFF` 是你吹气时它的吼叫。

## 4. v9 为什么错：一个"半对半错"的修复比全错更危险

### 4.1 v9 的推理链（看起来无懈可击）

1. 初版用 `raw >> 16`（取高 16 位）→ max 恒 0 ❌
2. 改成 `raw & 0xFFFF`（取低 16 位）→ max=32639 ≠ 0 ✅ "有数据了！"
3. 用 PB5 短接 3.3V 验证：全 1 帧 → 0xFFFF → abs=1 ✅ "链路通"
4. 结论：取低 16 位正确

### 4.2 三步推理里藏着同一个盲区

**当时麦克风已经坏了（MEMS 声学部分死，数字接口输出恒定值）**：

- `max=32639 ≠ 0` 里的 32639 = 0x7F7F，其实是坏麦输出的**恒定垃圾**，不是音频
- PB5 短接验证只证明"电信号能从 SD 线走到 RAM"，不证明"提取公式正确"
- **没有任何一步验证过"声音变化 → 数值变化"这条因果链**

> 类比：你的收音机坏了只会播同一段噪音。你调了个旋钮，噪音从"刺啦"变成"沙沙"，就断定旋钮调对了——但你从没听过电台，怎么知道沙沙就是正确的声音？

### 4.3 v10 才发现的真相：掩码没错，取样周期错了

`raw & 0xFFFF` 这个掩码**恰好是对的**（对 word[4k] 而言）！真正的错误在 `extract_frame` 的循环：

```c
/* v9（错误）：把 512 个字全部当成 512 个采样 */
for (i = 0; i < count; i++) {
    pcm[i] = I2S_DRV_ExtractPCM(src[i]);   // 4 个字里 3 个是垃圾！
}

/* v10（正确）：每 4 个字取 1 个 */
for (i = 0; i + 3 < count; i += 4) {
    pcm[out++] = I2S_DRV_ExtractPCM(src[i]);  // 只取 word[4k]
}
```

### 4.4 为什么错样本会让 max "看起来稳定"

max 是取**绝对值最大的那个样本**。512 个字里有：

- 128 个真样本：安静时 ±600 左右
- 128 个 `0xLL7F`：绝对值 ≈ 16000~32000（伪迹！比真信号大得多）
- 256 个 `0xFFFF`：绝对值 = 1

**max 永远被 128 个 `0xLL7F` 伪迹中的最大者拿下（~32000）**，真音频安静 ±600、吹气 ±30000 都撼动不了它——吹气时的真音频确实到了 ±30000，但伪迹也恒在 ~32000，两者叠加后 max 依然显示 ~32000。

> 类比：考试全班成绩取最高分。你们班（真音频）考 90 分，但名单里混进了 128 个"幽灵考生"每人恒定 99 分——不管你们班考多好，"班级最高分"永远是幽灵的 99。**统计量被假数据钉死，真数据再努力也看不见。**

## 5. 修复后的验证数据（17:58 复测）

| 状态 | max 实测序列 | 含义 |
|------|-------------|------|
| 安静 5.5s | 98 ~ 2352（典型 ~300） | INMP441 底噪 + 轻微直流偏置，正常 |
| 吹气 2.4s | 4577 ~ **32767**（多次打满 100% FS） | 吹气直达满量程，信噪比 ~40dB |

**判定依据**：安静/吹气的 max 差出 1~2 个数量级，"吹气 max 明显变化"（AC-04）成立 → 麦克风声学通道、接线、I2S 链路、提取算法**全链路打通**。

顺带核准了采样率：每半缓冲 128 真采样 × 125 帧/s = **16000 Hz 整**，与设计一致。旧文档"实测采样率 2 倍"的疑点是**把 DMA 字当采样点计数**造成的口径错误——512 字/帧被当成 512 采样/帧，算出来自然是 2 倍。这也解释了为什么这个"2 倍疑点"一直没人怀疑出真问题。

## 6. 经验教训（可迁移的规则）

### 教训 1：验证"信号链"必须验证"因果"，不能只验证"数值非零"

- ❌ `max ≠ 0` → 数据对了
- ✅ `输入变化 → 输出跟着变化` → 数据对了
**任何"A→B 因果链"的测试，必须人为扰动 A，观察 B。**（本例：对着麦克风吹气 = 扰动 A）

### 教训 2：测试器具本身坏掉时，得出的"通过"结论全部作废

v9 的三个"验证"全是在坏麦克风上做的，参考系（恒定垃圾输出）本身就不可靠。**换新器件后，旧结论要重新过一遍**——这就是为什么新麦到货后第一时间复测，立刻暴露了问题。

### 教训 3：RAW dump 是位对齐问题的"X 光片"

猜位对齐（>>16 还是 &0xFFFF 还是 >>8）是猜不出来的，50 行推理不如一行：

```c
printf("%08lX %08lX %08lX %08lX\r\n", raw[0], raw[1], raw[2], raw[3]);
```

**先看原始数据长什么样，再写提取代码。**周期性模式（本例 4 字周期）用肉眼就能从 hex dump 里看出来。

### 教训 4：max/min 这类"极值统计"对污染样本零抵抗力

max 会被单个异常样本钉死，mean 会被直流偏置拉偏，RMS 对两者都更稳健。**调试期打印多个统计量（max/mean/RMS），交叉印证**，可提前发现"max 稳定但 mean 诡异"这类矛盾信号——v9 时代如果有 mean 输出，会发现 mean 恒 ~-1（被 0xFFFF 主导），和 max~32000 的矛盾早就报警了。

### 教训 5：I2S 器件数据手册的"槽格式"必须和主控的"字格式"逐 bit 对表

INMP441：24-bit 数据 + 1 bit 标志，只在槽前 25 SCK 驱动，槽内剩余 SCK 及整个右槽高阻。
STM32：32-bit 字窗口，不区分槽内真假。
**错位半槽（16 SCK）后，"哪个字是真数据"完全取决于两器件的相位关系——必须实测，不能推算。**

### 教训 6：先查手边的资料，再现场推导（本项目最痛的一条）

事后复盘发现：**这个 bug 的答案和排查方法，从项目一开始就躺在自己的文档里**。

- [CubeMX_I2S3配置详解.md §0.4](../../CubeMX_I2S3配置详解.md)（配置阶段产出，先于 BUG-002 十余天）：
  - 时序图 `SD: zz MSB...LSB zz zz` 中的 `zz`（高阻态）正是 4 字周期垃圾的来源——高阻段被上拉电阻拉成 `0xFFFF`/`0x7F`
  - 末尾警告框**原话**："建议第一版先用 `printf("%08lX", raw)` 打印原始 16 进制值，确认实际数据分布后再确定移位方案"——这就是 8/28 才做的 RAW dump
  - `外部资源索引.md` 第五节明确标注 INMP441.pdf 和 ESP32 示例"已读取"，ESP32 作者踩坑记录（"只能 32-bit""数据可能要做位处理"）也早已收录
- 但 8/16 调试 BUG-002 时进入"掩码猜谜"隧道视野（>>16 → 失败 → &0xFFFF → "成功"），没有回读预研文档；8/28 处理"吹气无响应"时又从头推导了一遍 RAW dump——**重新发明了 12 天前就写好的排查方法**。

> 类比：家里药箱第一层就放着对症的药，说明书都翻好夹了书签，但你头疼时直接冲去医院挂了个专家号——折腾一圈回来，医生开的正是药箱里那盒。
>
> 已固化为 **R26 规则**：调试外设问题前必须先查 `外部资源索引.md` 和预研文档中该器件的章节。
