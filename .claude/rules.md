## §3 L2 流程规则（开发/测试/评审流程场景触发）

\[R8] 生成代码前置三层校验：优先复用 HAL 标准库 → 复用现有 BSP 模块 → 用 .skills\codegraph.bat explore 检索调用链，无复用才编写最小代码。

\[R31] 编码前预研门控（2026-09-01 A4-02 事后追加）：任何新增功能性代码（含"看似机械"的小改动）落盘前，必须自问"这个模式的坑我查过三源吗？"——查过才写；没查过先查再写。commit 钩子只验交付物存在，验不了时序；违反时序的行为须在文档中登记"先写后研"偏差并补研闭环。纯 §5 快速路径（改宏/注释/路径）豁免。

\[R32] 完整研发操作流程（总纲，2026-09-14 自 embedspec 模板镜像）：任何功能性开发按此八步推进，步骤③⑤⑥⑦⑧涉及外部来源时遵循 R27/R28 口径。缺任一步骤需在 FEAT 文档登记偏差：
1. **预研**：找正确、成熟方案。来源池 = 官方仓库 + 权威个人平台（大牛博客/高星个人项目）+ 本项目预研文档，至少对照 1~2 个实现。
2. **排雷**：查 Issue 区（官方 + 参考实现）看已知坑——API 误用、边界条件、版本坑（R27 源②）。
3. **预防**：向权威技术来源/专业实践学习如何规避坑（官方文档、权威博客、高星开源项目经验、Stack Overflow 已答案例等），别掉进坑。把"坑→后果→预防→验证判据"写成坑清单（R27 源③），并入设计汇总防御节。
4. **影响分析**：列出改动影响——是否影响前面已有的内容（不兼容？破坏地基？），用影响地图明确"不触什么"与零冲突面（R9/R29②）。
5. **资源预算**：占用多少资源（CPU/RAM/栈/串口带宽），量化（R29③）。
6. **复用**：开始复用成熟方案，按 R28 核对硬件一致性，能照抄的照抄、禁止照抄的电学调优值另取本硬件实测来源。
7. **遇意外**：出现预料之外的问题 → 去权威技术网站找答案（Stack Overflow 最常见，含 SO 在内的权威平台均可：官方文档/讨论区/知识库/专业博客等）+ 看 codegraph/grep 交叉确认问题根因（R21 证据：修复须带复现前后对比 + 验证条件 R25）。
8. **审查**：最后 review（R23，触发 requesting-code-review 按 AC 逐条打勾），通过才标记完成。

2. **Issue 区**：官方/参考仓库的 Issues（搜关键词 + 已关标签）是踩坑富矿——API 误用、边界条件、版本坑往往不在 README 里（用 `github.com/<repo>/issues?q=<关键词>` WebFetch）；
3. **坑清单交付物**：预研结论必须含"坑与预防"表（坑→后果→预防→验证判据），并入设计汇总防御设计节——没有坑清单的预研视为未完成。
   纯 CubeMX 模板类机械改动（改引脚/加外设初始化）可豁免。项目内已有可复用模式（如 i2s\_drv 回调架构、A2-01 的 vendored 集成模式）时，复用优先于外部检索。

\[MUST]\[R28] 从 GitHub 抄成熟代码时，必须先核对**硬件一致性**，按层分类决定抄什么：

* ✅ 可直接照抄（硬件无关）：协议帧格式、调用流程、数据结构、架构分层（如 4ilo 的 HAL\_I2C\_Mem\_Write 0x00/0x40 寄存器模式）。

* ❌ 禁止照抄（硬件强相关）：**电气参数/时序调优值**——SSD1306 的 0xD5 振荡/0xD9 预充电/0xDB VCOMH/0x81 对比度、上拉/驱动强度、时钟树配置等，是原作者对其具体模块/芯片的调优值而非标准值，**跨硬件不可移植**。此类值必须采用与本硬件实测跑通的来源（优先级：本块硬件实测过的工程 > 器件数据手册推荐值 > 开源默认值），并在代码注释注明来源与差异。

* 优先检索顺序：与本硬件同型号同封装且实测跑通的项目 > 官方仓库 > 高星通用库（案例：OLED 排查走了 4 轮弯路——真根因是 BUG-20260829-006 的调度器时序；参数照搬是其中两轮弯路的直接推手）。

* **R27 预研三源 pre-commit 检查**（2026-08-30）：提交时检测 staged 代码（firmware/soundDog 非库区 .c/.h）是否新增 HEAD 中 soundDog 树从未用过的 `arm_*` API 符号；有新 API 则要求**同一提交**的 staged 文档/注释新增行含三源证据标记：源①"源码"（被调函数源码阅读）、源②"issue"（Issue 区调研）、源③"坑"+"预防"（坑清单交付物）——缺任一即拦截。豁免口径与规则一致：复用已有 API 自动放行（R8）、机械改动无新 API 自然放行（§5）、逃生口 `--no-verify` 登记理由。实现：[scripts/check\_r27\_research.ps1](../scripts/check_r27_research.ps1)；已双向实测（拦截/复用放行/证据放行三案例，2026-08-30）。

* **\[MUST] 含中文的 .ps1 脚本必须存为 UTF-8 with BOM**：Windows PowerShell 5.1 对无 BOM 文件按 GBK 解码，中文注释行尾字节可与换行符组成非法双字节序列，把**下一行代码吞进注释**静默改变逻辑（2026-08-30 实测：check\_r19\_zone.ps1 的 `$violations +=` 被吞，脚本永远放行；加 BOM 后拦截恢复正常）。新建/编辑 .ps1 后用 `Format-Hex` 验证首字节为 `EF BB BF`。**注意（2026-08-30 二次实证）：编辑器/Edit 工具保存会剥掉 BOM 导致脚本静默失效（实测安装器无输出即中招）——每次编辑后必须重加 BOM 再验证**。hook 文件本身须首行 shebang `#!/bin/sh`（Git for Windows 的 sh 无法 spawn 无 shebang 的裸命令行脚本）。
